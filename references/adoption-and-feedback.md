# 项目采用判断与试用反馈

仅在用户问“对我的项目有没有用、要不要换、先试哪个”，或带回真实试用结果时读取。普通收藏整理沿用原流程，不为每条材料强加项目问卷、长报告或数字评分。复用本轮已知目标和约束，只补会改变判断的关键缺口；既有明确的实施或归档授权继续有效。

## 判断这次是否值得用

先用用户指定的项目资料或本轮已核实事实确认：当前要改善什么、现有方法如何完成、什么必须保持。不要因工具新、演示漂亮或来源热门，就默认替换现有方法；也不自动扫描无关项目。

沿一条短链给结论：**当前问题 → 现有方法 → 新方法改变哪个环节 → 净价值与代价 → 保留 / 小测 / 采用**。净价值可以定性说明，不是相减得到的虚构数字。

- 以真实卡点为基准，包括继续现有方法或暂不做。没有项目事实时只给候选用途与一个决定性缺口，不宣称已适配。
- 每个关键优势回指来源证据；区分作者演示、用户反馈与本次实际验证。说明可迁移的条件、引入/维护/切换成本、会损失什么；未知数字保留未知。
- **保留**：不改善当前卡点、违反硬约束，或收益不足以抵消已知代价。说明什么新证据会改变判断；不为给行动而强行建试验。
- **小测**：值得解决的卡点已匹配，但关键能力或代价未验证。只建议一个能改变结论的最小比较：同一输入/任务、当前方法作对照、观察什么、什么结果继续或停止。验收条件来自用户目标或已有标准；没有数字依据就用可观察条件，不编造提升率、工时或成功率。
- **采用**：所需关键条件已有证据且代价可接受，标明采用的具体范围。局部验证只能支持局部采用；判断不自动等于部署、付费、建卡或发布。

放进原条目 report.md 的行动建议/最终判断或对话结论即可。用户选定行动后，按既有授权交给原执行流程；不用另建评分库或决策数据库。

## 真实结果回连

用户带回结果或本轮已授权验证结束时，先定位原推荐/报告与当时待验证的命题，再读取实际结果。原报告与来源证据保持原样，不倒改过去的推荐来迁就新结果。

简要留下四件事：**原判断及链接；实际条件；观察及依据；现在如何调整**。实际条件按结果相关性记录版本、日期、输入/任务和环境；缺失就写缺失。用户说“快但更容易变脸”是用户反馈，不能换算成毫秒或失败百分比，也不能写成 Agent 独立实测。

- 分别更新具体命题：速度改善不证明质量也达标；任务跑通不证明收益；卡片完成/放弃不是效果证据。
- 结论可以支持、收窄或撤回原建议。只有同样版本与条件的失败才用于阻止重复推荐；版本/条件变化时说明旧结果的适用边界，只在变化与旧失败有关时提出针对性复测。
- 新资料分析前，按实体、原来源 ID 和项目问题检索这类结果。优先使用相关的真实试用证据，引用其日期与条件；不能因为新宣传又把已失败方案写成无条件推荐。
- 没有真实结果时保持待验证。无需为补齐表格重跑旧测试，或为了确认一个方向重复研究整个来源。

仅反馈讨论时在对话交付。已有本地归档/结果回填授权时，按 [归档约定](archive.md) 为原条目新建日期版本并链接旧版；多来源比较存入既有 digests 路径。沿用 report.md/sources.md/INDEX.md，不建另一套数据库或待办系统。新版本记录原报告路径、来源 ID/URL、项目问题、试用版本和结果依据；未知项写未知。后续查询优先定位该来源/项目的最新结果版本，同时保留原结论的时间条件。用户已有可引用的项目试用记录时链接该记录，不复制第二份；本地版本 complete 只表示本次分析完成，不代表方案已经部署成功。

## 三个对照例子

以下均为虚构案例，只示范判断方法；执行时使用真实材料。

1. **卡点不匹配**：用户的连续角色视频卡在人工修脸，收藏 A 的证据只证明渲染更快。不要只写“可提高视频生产效率”；应写“先保留现有方案，A 未证明能减少修脸；等渲染成为实际瓶颈或出现一致性证据再评估”。不估算省几小时。
2. **匹配但未验证**：用户要求导出文件能直接进入现有剪辑工程，收藏 B 的 README 声称支持该格式，尚无本地证据。不要直接建议迁移；建议在已有授权下用一段现成代表性素材导出并导入工程，对照当前工具检查必要轨道、时间码和画面是否保留。通过只支持该素材类型的小范围采用，失败则继续原工具并记录阻塞项。
3. **证据改变范围**：用户报告 v1.2“确实快，但会变脸”，未给测时和失败数量。应将速度记为用户反馈，把连续人物镜头暂时排除；不能虚构准确率。之后 v1.3 只有“稳定性改进”的发布说明时，保留原结论为 v1.2 条件下成立，最多建议针对变脸问题复测，不宣称已经修好，也不永久否定所有版本。

## 轻量验收

用 [离线案例](../tests/adoption_cases.json) 做前向验证：让未参与编写的 Agent 只读取本 Skill、当前案例的 `request` 与 `materials`，在对话中给结论；不提供 `checks`。完成后逐项核对 checks，并由审阅者检查关键结论能否定位到材料。关键断言无来源、虚构数字、无视硬约束，或把反馈当独立实测，任一项出现就不通过；不用总分掩盖失败。案例只是回归夹具，不证明实际工具效果。

从 Skill 根目录运行以下只读命令可提取不含 checks 的测试输入，交给另一位 Agent；它不会执行案例中的工具或业务动作：

```bash
python3 -c 'import json; from pathlib import Path; d=json.loads(Path("tests/adoption_cases.json").read_text()); print(json.dumps([{k:c[k] for k in ("id","request","materials")} for c in d["cases"]],ensure_ascii=False,indent=2))'
```
